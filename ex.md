## 1. Зачем эта лаба

ЛР2 учила писать **юнит-тесты** — проверять каждый модуль по отдельности. ЛР3 — следующий уровень:

- **Интеграционные тесты** — проверять не отдельные функции, а *взаимодействие* нескольких модулей в цепочке (ввод → валидация → база данных → внешняя отправка).
- **Тестовые заглушки (mock/стабы)** — подменять в тесте то, что нельзя или нельзя трогать: пользовательский ввод (`input()`) и выход наружу (email-сервер). Это даёт *изоляцию*: тест управляет входом и наблюдает выход, не завися от реальной клавиатуры и интернета.
- **Полное покрытие кода** — каждая строка проекта должна хотя бы один раз выполниться в тестах (проверяется инструментом `coverage`).

### a. `validation.py` — класс валидации

Класс `RegistrationValidator` содержит **ровно один метод** `validate(login, password, confirm)` — это та же логика проверки регистрации из ЛР1, перенесённая в класс (требование ТЗ п. a):

- логин: не пустой, не из чёрного списка, формат телефона `+x-xxx-xxx-xxxx` или email или латиница/цифры/подчёркивание от 5 символов;
- пароль: от 7 символов, кириллица (верхний + нижний регистр), цифра, спецсимвол, совпадает с подтверждением.

Возвращает пару `(True, "")` при успехе или `(False, "сообщение_об_ошибке")`.

Две вспомогательные проверки (`_validate_login`, `_validate_password`) вынесены **на уровень модуля** — чтобы класс оставался «однометодным», как требует ТЗ, но код не распух.

### b. `db.py` — класс базы данных

Класс `RegistrationRepository` поверх встроенного **SQLite** (`sqlite3`, файл БД не нужен — используется `:memory:`, база живёт только во время теста).

Таблица `registrations`:

| login | password | confirm | result | error |
|---|---|---|---|---|
| ivan_2026 | Пароль1! | Пароль1! | 1 | '' |

- `result` — результат авторизации (0/1, в Python возвращается как `bool`);
- `error` — сообщение об ошибке (пустое, если всё хорошо);
- ** первичный ключ — тройка (login, password, confirm)**: каждая запись идентифицируется именно тремя полями, как требует ТЗ.

Методы: `add()` (добавить), `get()` (получить запись или `None`), `delete()` (удалить, возвращает `True`, если строка была), `close()`.

### c. `user_interface.py` — интерфейс ввода

Абстрактный базовый класс `UserInterface(ABC)` с единственным абстрактным методом `get_credentials()` — это **интерфейс**: он задаёт контракт «откуда-то получить тройку (логин, пароль, подтверждение)», но не знает, откуда именно.

Конкретная реализация `ConsoleUserInterface` спрашивает данные через `input()` и возвращает очищенную от пробелов тройку. Благодаря abc в тесте этот класс легко подменяется заглушкой.

### d. `external_dependency.py` — сторонняя зависимость

Абстрактный `ExternalDependency(ABC)` с методом `send(payload)` — интерфейс «куда-то отправить строку-результат».

Конкретный `EmailServerStub` — **имитация email-сервера**: реальной отправки нет вообще, сообщение просто складывается в список `outbox`. По условию ТЗ класс делает *исключительно имитацию* передачи данных.

### e. `controller.py` — класс-контроллер

`RegistrationController` собирает все части в **сквозной сценарий** (метод `run()`):

```
┌─────────────────────────────┐
│ 1. user_interface.get_credentials()   ← спросить данные у пользователя
├─────────────────────────────┤
│ 2. repository.get(...)      ← есть запись в БД?
│    ├─ НЕТ → validator.validate()  → repository.add()   (вычислить и сохранить)
│    └─ ДА  → взять result/error из БД                   (взять из кэша)
├─────────────────────────────┤
│ 3. external.send(message)   ← отправить строку-результат наружу
├─────────────────────────────┤
│ 4. return message           ← вернуть результат операции
└─────────────────────────────┘
```

Вся бизнес-логика — в одном месте; каждая зависимость (ввод, БД, валидатор, отправка) передаётся в конструктор — это и позволяет в тестах подменять любую из них.

## 3. Как устроены тесты

Файл `tests/test_lab3.py`, запуск: `python -m unittest discover -v` из папки `Lab3_АгиенкоДА`.

### Интеграционные (4 шт., минимум по ТЗ) — класс `TestIntegrationController`

Каждый тестирует **полный путь через Controller**: реальный валидатор + реальная БД в памяти + `ConsoleUserInterface` с подменённым `input()` + внешняя зависимость (стаб или мок).

| # | Тест | Что доказывает |
|---|---|---|
| 1 | `test_first_run_sends_result_and_stores_record` | Первый прогон: данных в БД нет → валидация прошла → запись появилась в БД → строка-результата ушла в `outbox` внешней зависимости |
| 2 | `test_second_run_takes_result_from_db_without_revalidation` | Повторный прогон: запись уже в БД → результат взят из неё, **валидатор подменён моком и упадёт, если его хоть раз вызовут** → дублей записи в БД не появилось |
| 3 | `test_invalid_data_stored_with_error_and_message_sent` | Невалидный ввод: в БД сохранена запись с `result=0` и текстом ошибки, наружу ушло «отклонена» |
| 4 | `test_all_validation_rules_reached_through_controller` | Все правила валидации (10 отказов по логину, 7 по паролю, несовпадение подтверждения, 3 успешных типа логина) прогоняются **сквозным сценарием**: проверяется поведение сценария (запись в БД + отправленное сообщение), а не тексты ошибок |

Тест 2 — самый показательный: он доказывает ветвление «если записи нет → вычислить, если есть → взять из БД» именно *интеграционно*.

### Юнит-тесты (4 шт.) — новые модули, **без дублей ЛР2**

| Класс тестов | Что проверяет | Заглушки |
|---|---|---|
| `TestDatabase` (2) | `add → get → delete` по тройке-ключу; `get` неизвестной записи возвращает `None` | — |
| `TestExternalDependency` | стаб кладёт всё в `outbox`, `send` возвращает `True` | сам стаб и есть имитация сервера |
| `TestUserInterface` | консольный ввод отдаёт очищенную тройку | `patch("builtins.input", side_effect=[...])` — **имитация пользовательского ввода** |

**Про дубли с ЛР2:** правила валидации из ЛР2 (тексты ошибок) в юнит-тестах ЛР3 **не повторяются** — юниты трогают только новые модули (БД, внешняя зависимость, ввод). Сами правила прогоняются в интеграционном тесте 4, где проверяется не текст ошибки, а поведение сквозного сценария: отказ → запись в БД с `result=0` и непустой ошибкой, успех → запись с `result=1` и ушедшее сообщение.

### Заглушки в действии (ключевое требование ТЗ)

```python
# имитация пользовательского ввода — input() в тесте не спрашивает человека:
with patch("builtins.input", side_effect=["ivan_2026", "Пароль1!", "Пароль1!"]):
    message = controller.run()

# имитация внешнего сервера — сеть не трогается, вызовы перехватываются:
external = Mock()
...
external.send.assert_called_once_with(message)
```
